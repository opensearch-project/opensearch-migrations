# Capture and replay hardening changelog

Audit date: 2026-10-02

This changelog records externally meaningful differences between upstream mainline and the capture/replay
hardening candidate. It is a release and compatibility record, not an authoritative design document.

Comparison pins:

- Integrated upstream mainline: `dcf88fc9688cd6a8cb257d75873692a4b7839195`
- Audited implementation candidate: `8aa7a526f60afb7a589b74610d839004a9509330`
- Common merge base: `a960887ba76eb0d3c6d2a252bc553fee339d3318`
- Behavioral evidence restoration: `94be4a5049e065a416558070987961096214cdf0`

The candidate SHA is the merged implementation baseline. This changelog and the audit corrections
identified while writing it are applied afterward and do not alter the authoritative designs under
`docs/captureAndReplay/`.

Compatibility terms used below:

- **Breaking**: an existing caller, configuration, capture, or operational assumption must change.
- **Intentionally incompatible**: compatibility was deliberately not retained.
- **Preserved**: the implementation changed, but the named observable contract remains.
- **Additive / stricter validation**: existing valid use remains valid, while new behavior or earlier
  rejection was added.

## User-facing changes

User-facing includes migration configuration authors, CLI users, operators, and consumers of captured
traffic or operational telemetry.

TLS-failure evidence did not require a finalized capture record. | Whole and segmented source interim responses have typed observations. `ConnectionExceptionObservation` is diagnostic: it does not close the connection or reset the request in flight; captured close and broker-time expiration remain distinct. ## Settled compatibility decisions and known limitations

These are the decisions and limitations a maintainer could otherwise accidentally reverse during review or
cleanup. Each entry explains why it matters, the candidate's behavior, and the consequence. An unresolved
item is explicitly not a new compatibility promise.

| Concern | Why it matters | Candidate decision or current behavior | Consequence and follow-up | Evidence |
|---|---|---|---|---|
| Managed topic timestamps | Live replay expiration and heartbeat logic require broker time, while the append time of a BYOC import is merely its load time. | Managed live-capture topics default to and require `LogAppendTime`; managed S3/BYOC topics default to and require `CreateTime`. ## Mainline integration confirmation

The merge candidate retains the following mainline changes introduced after the rebuild branch point:

- All 12 Gradle repository-routing and credential-isolation tests passed.
- EKS NodePool override examples lint and render successfully, and both CDC pipelines retain live
  post-workload verification.
- Label-triggered Jenkins workflow expressions survived the merge.

These are integration checks, not branch-authored changelog entries. No branch-authored test-evidence
regression remained after restoring focused coverage for retry policy, accepted Kafka record sizing, S3
shutdown durability, restart/cut-point reconstruction, and null connection-ID diagnostics.
