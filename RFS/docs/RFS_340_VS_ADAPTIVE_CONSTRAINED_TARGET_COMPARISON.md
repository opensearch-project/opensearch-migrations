# RFS 3.4.0 vs adaptive flow control on a constrained target

Status: complete through the RFS 3.4.0 checkpoint at 2026-11-01 22:08:53 UTC.
The old-image migration continued after this report was generated; the
comparison and plots intentionally stop at this checkpoint so both runs cover
the same 3h04m17s of target-writing time. The report can be extended with a
later checkpoint without changing its method.

## What this comparison can answer

This is a useful operational comparison of two configurations against the same
constrained Amazon OpenSearch Service domain:

- the current adaptive-flow-control image with the high-concurrency settings
  used by the pressure test; and
- the released RFS 3.4.0 image with its default bulk concurrency and sizing
  controls.

It can answer whether the released defaults make more or less progress, and
create more or less target pressure, during the same elapsed time on the same
target.

It is **not an image-only A/B test**. The image and the concurrency policy both
changed. If the old/default run is faster, that does not by itself prove a code
regression in the adaptive implementation. A third run using the new image
with the old run's effective bulk settings would be needed to isolate the image
change.

| Dimension | Adaptive pressure run | RFS 3.4.0 default-bulk run |
|---|---:|---:|
| Image | Current adaptive image, digest ending `5aae` | Public 3.4.0 release, digest ending `c923` |

| Fleet connection ceiling | 1,440 | 240 |
| Bulk byte ceiling | 10 MiB | 10 MiB |
| Bulk document ceiling | 20,000 | 2,147,483,647; byte ceiling normally binds first |

| New cut/backoff/split metrics | Emitted | Not present |
| Bulk response timeout override | 310 seconds | Newer option absent in 3.4.0 |

The 3.4.0 release parser does not recognize four fields generated by the
current workflow: `bulkResponseTimeout`, `disableFailedDocumentStream`,
`maxFailurePercentToFailDocuments`, and `maxLeaseDuration`. A parser probe
confirmed that removing only those four fields makes the generated payload
compatible. The one-off deployment was patched before the measured data window.
All 24 final-revision workers were ready with zero restarts when the clock
started.

At this checkpoint, the old/default configuration made 15.5% more progress
while its maximum sampled target write queue was 72% lower. Both runs kept all
24 workers ready, drove at least one target data node to 100% CPU, and produced
no write or indexing-pressure rejection delta during the compared window.

This result does not by itself say why. The most likely explanation to test is
that the new run's 60-connection ceiling lets each worker repeatedly probe above the sustainable
target rate, receive 429 feedback, cut its allowance, and repeat. The released
10-connection default may stay closer to this target's sustainable operating
point and avoid that cycle.

That would be a configuration/policy interaction, not automatically an
adaptive-code regression. A future new-image-at-10-connections control is
needed to distinguish those cases.

## Known limitations and confounders

- The comparison intentionally changes both image and connection policy.
- The adaptive run used a 20,000-document ceiling; RFS 3.4.0 used its default
  unbounded document ceiling. Both used the same 10 MiB byte ceiling.
- The adaptive run happened first. Deleting the target index reclaimed its
  data, but the domain was not restarted, so caches and JVM history were not
  reset.
- The target's rejection counters are node-lifetime counters. The second run
  started after the adaptive run had already added two indexing-pressure
  rejections, so the report compares each run's delta rather than the absolute
  counter.
- Local AWS credentials expired during the adaptive run, creating an
  approximately 14-minute monitoring gap. RFS and the target continued
  running. Cumulative target counts before and after the gap are valid; fine
  detail inside that interval is unavailable.
- RFS 3.4.0 does not emit the newer adaptive allowance, cut, wait, split, and
  retry metrics. Empty dashboard regions during its time window are expected,
  not evidence of zero activity.
- This report compares partial migrations at an in-flight checkpoint, not
  completed migrations. It uses target counts from the matched monitoring
  samples; neither compared window includes a post-scale drain.

## How to read this checkpoint

1. Compare cumulative documents at exactly 11,057 seconds.
2. Compare trailing 10-minute throughput over the whole interval, not a single
   peak.
3. Align throughput dips with cumulative shard completions. A dip with a shard
   wave and lower target activity is normal work transition; a dip with
   retries, cuts, queue growth, or rejections is backpressure.
4. Compare maximum and sustained write queue, target rejection deltas, health,
   blocks, node continuity, and terminal failures.
5. Treat the adaptive cut count as explanatory telemetry for the new image,
   not as a direct old-vs-new metric.

If the old/default run finishes materially ahead with lower pressure, the next
clean isolation test should use the new image with 10 maximum connections per
worker and the default document-count ceiling. That would hold the effective
traffic policy much closer to RFS 3.4.0 and reveal whether the remaining
difference belongs to the image or to the high-ceiling adaptive policy.
